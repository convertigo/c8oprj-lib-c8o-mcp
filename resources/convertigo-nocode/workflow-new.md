# Workflow steps 0 to 3

Read it before creating an application or a form. Summary: `SKILL.md`, in this folder.

---

0. For a new application over business records (a list, an entry form, the detail of a selected row, a dashboard, on new or existing Baserow tables), call `nocode-app-create` first, once, with the business spec: the entities, their fields and choices, the screens wanted. Do not read the contract or write reduced JSON for it. The tool creates the Baserow base, tables and fields (or reuses an existing table given by its id from `nocode-baserow-catalog-list`), then the form with custom navigation, a home page when needed, return buttons, a list with an always visible search bar and choice filters, a read-only detail, an entry form whose save adds the row (toast, list refreshed, page emptied, back) and a grouped chart. Name fields in the user's language as the list headers should read, and give each screen the `title` the user calls it (Historique, Nouvelle visite): pages, headers and the buttons that open them take it. Without `baserow`, the tool uses the base of the existing tables or creates one in the user's only workspace; with several workspaces it answers them and you ask the user which one. It answers a short outline (form id, tables, pages, components, bindings): report it, and make any further change with `nocode-form-edit` on that id (read the contract for that), never by calling `nocode-app-create` again. Use the steps below for what it does not build: a form asked for alone, a questionnaire, conditions or calculations, an update or a deletion from the detail.
1. Read the no-code contract with `nocode-form-contract-get` once per conversation, in one call that names its core `quickReference` (the form, pages, components, conditions, defaults, flows, Baserow sources and saves, edit operations) with what the task needs:
   - a form or a questionnaire, on one or several pages, with choices, conditions or required fields: `sections:["quickReference"]`, nothing else;
   - an application with a home page, buttons and flows: `sections:["quickReference","generationQuality"]`;
   - a change to a form: `sections:["quickReference","editTool"]`.
   Ask another section only for what the core does not show: `styles` for a style recipe, `componentAuthoring` for a component option, `flowAuthoring` for a flow element, `dynamicReferences` for a SmartSource reference, `baserowSources` or `backendActions` for a native variable or another backend sequence. One answer holds what fits (about 12,500 characters) and names the others in `remaining`: ask them in the next call. Return each answer from its own call, never several merged in one result. Do not call the contract again for a part you already have, and do not cut its answers.
   Called from code (`run_typescript`), a tool is `tools.mcp_Convertigo.<its name with underscores>`. These need no `search_tool_functions`; call them with exactly these arguments: `nocode_form_contract_get({ sections })`, `nocode_form_create({ reduced })` (`reduced` an object), `nocode_form_get({ id, find })` (`find` optional), `nocode_form_edit({ id, operations })` (the operations of the contract's `editTool` section), `nocode_form_preview_capture({ formId, page, device })` (`page` and `device` optional), `answer_page({ answerId, page })`. For another tool, load its schema with one `search_tool_functions` `{ mode: "details", functions: [...] }` naming every tool the task still needs; never look up a tool named here with `best_match`. A refused argument (`invalid_arguments`) lists the allowed ones: fix the call, do not search. `nocode-form-validate` checks a whole form document you hold (`form`, an object), never an id: a saved form was validated by the create or edit that saved it.
   A long answer comes as a `partialAnswer` of two pages or more: its short fields (`status`, `saved`, `id`, `rev`) come with it, but `r.form` and `r.validation` are undefined until its pages are joined. Never call a write again because a field is missing: read every answer through this helper, in the script that calls the tool:

   ```ts
   async function whole(r) {
     const p = r.partialAnswer;
     if (!p) return r;
     let text = p.text;
     for (let page = 2; page <= p.pages; page++)
       text += (await tools.mcp_Convertigo.answer_page({ answerId: p.answerId, page })).partialAnswer.text;
     return JSON.parse(text);
   }
   ```

   Then read `status`, `saved`, `id`, `rev` and `validation` after a create or an edit, not `result`, which does not exist. A refused call answers too, with `saved:false` and `validation.issues` or `error`. A saved form lists its components in `form.formulaire` (type, name, `config.label`, `config.page`, `config.mandatory`; the options of a choice are its `children`, `[{ value, selected }]`), its pages in `form.pages` and its flows in `form.flows`. Return only what you check, never the whole form.
2. Build or patch only the reduced no-code form JSON unless the user explicitly provides a full form document for validation.
3. For new forms:
   - Choose navigation deliberately. For an application with a home/dashboard and task pages, prefer `navigationMode:"custom"` with native buttons linked to `push_page` flows (unique page names in reduced `targetPage`). Provide entry and return paths. Use tabs when requested or when peer sections genuinely benefit from them; use automatic page buttons for a linear questionnaire. The compiler's legacy fallback to tabs is not a design recommendation.
   - Assign a meaningful page `iconName` to every page by default. Prefer simple Ionic base icon names known to persist in C8Oforms tabs, such as `home`, `business`, `people`, `person`, `calendar`, `calendar-clear`, `list`, `document-text`, `receipt`, `settings`, `stats-chart`, and `search`. Avoid `*-outline` icon names unless the user explicitly requests them and the saved document confirms they render.
   - Add a modern, domain-appropriate `wallpaper` and matching `thumbnail` by default when the no-code form contract supports them. Prefer clean, professional visuals that do not reduce form readability; skip or simplify the background if it would distract from data entry.
   - Use multi-column layouts when the no-code contract supports them and the fields naturally group together. Prefer `layout` fields containing related child fields. Use 2 columns on desktop/tablet and collapse to 1 column on phones. Avoid cramped columns.
   - Create incrementally (a data application is created in one call by `nocode-app-create`, step 0). A tool argument is text the model generates token by token: beyond roughly 4 KB of reduced JSON a structural typo is likely and the call is refused. Step 1: `nocode-form-create` with the skeleton (name, navigation, pages with header and icons, fields grouped in sections and action layouts with type/name/label/mandatory/choices, Baserow sources and actions with their columns, button fields with variant and flow ids, push_page/submit flows) and no style objects: the compiler spaces an application by role; pass `reduced` as a JSON object, not a string. Step 2: one `nocode-form-edit` per page for what remains (`add_flow_element` for toasts and refresh, `update_field` for a deliberate style change, `update_page` for flags). Step 3: read `validation` in the answer of the last create or edit; every design warning of step 1 must be resolved before delivery. Only a small form (a page or two, a handful of fields) may be created in one call with its styles.
   - Before compiling, apply the native design pass below to every page (in step 2 when creating incrementally). Functional components alone are not a finished application: choose spacing and grouping deliberately, then author the actual style objects rather than merely describing the intended appearance.
   - Use `nocode-form-compile` to convert the reduced JSON.
   - Use `nocode-form-validate` only on a whole form document you hold and have not saved: a create or an edit answers the validation of what it saved.
   - Use `nocode-form-create` only through the integrated No Code Studio authentication context.
   - For new Baserow connections, supply the discovered table identity, columns and business mappings but omit `form_id`, `source_id` and `source_owner` from `forms_config`. The create tool assigns these itself from the saved document and authenticated creator. `bindingFinalization.status:"pending_creation"` / `baserow_identity_pending_creation` from compile are expected, nonblocking: continue with create rather than inventing identifiers or claiming a No-Code limitation.
   - Inspect creation's `bindingFinalization`: `ready` confirms saved identities, not a tested business save. If `saved:true` with `status:"partial"` and finalization `pending`, a form already exists. Follow the returned recovery operation: `nocode-form-edit` with only `[{action:"finalize_baserow_bindings"}]` on the returned id. Never call create again to repair this result. The creator-only recovery is idempotent; if it remains blocked, report that existing id and the diagnostic instead of declaring the app ready.
   - In the script that creates the form, check in its answer that the chosen navigation persisted (the flags of `form.pages`, `form.flows`) and return only that check; do not read the form again. Custom navigation requires automatic tabs/buttons disabled and working native button flows. Tab navigation requires the intended tab flags and valid icons. Repair only the chosen style; never restore tabs over an intentional custom/button design.
   - Also inspect the saved `wallpaper` and `thumbnail` when a polished background/thumbnail was intended. If create/compile normalized them to disabled placeholders and the no-code contract exposes a supported wallpaper/thumbnail shape, immediately repair them with `nocode-form-update`; otherwise report that the current no-code contract did not provide a persistable wallpaper/thumbnail shape.
