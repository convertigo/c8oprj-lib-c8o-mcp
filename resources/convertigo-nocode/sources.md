# Sourceable Components and Baserow Source Pattern

Read it before connecting a component, a choice list, a save or a deletion to Baserow. Summary: `SKILL.md`, in this folder.

---

## Sourceable Components

- Any sourceable no-code component can be connected to an external source when `config.sourceEnabled=true` and the component has an enabled entry under `sources`. A map is the exception: see Maps below.
- In a saved C8Oforms document, find the sourceable component in `formulaire[]` by `type`, `name`, or `id`. The live source connection lives on that same component under `sources`, not in `pages[]`.
- Source entries are keyed by requestable name, for example `sources["lib_BaseRow.formssource_GetTableData"]`. Each source entry has `enabled`, optional `fullsync`, and source-specific `vars`.
- For sourceable components, inspect `component.sources` as the source of truth for live data binding. Component-local config such as grid `config.columns` or select static choices may be fallback, local, or historical configuration when a dynamic source is active.
- In a saved source config, `source_id` must match the component id. The create tool sets it automatically for new bindings; use that match to verify the saved result, not as a prerequisite to creating the form.
- Preserve unrelated source variables when changing a source connection, and update through no-code tools only. Avoid replacing the whole component or page when a minimal semantic edit or merge patch can change the source safely.
- When using hidden source grids only as data providers for visible cards, summaries, or SmartSource-rendered HTML, put those grids inside a dedicated `layout` and hide the layout with the component visibility option/condition. In persisted forms, prefer a `visibleIf` condition that can never be true (reduced `visibleIf:{never:true}`), and keep layout column sizes at `0` only as a defensive fallback. Do not rely on zero-width layout columns alone as the hiding mechanism.
- Hidden data-provider grids should usually use `config.returned_value="all_the_data"` so visible components can read the first rows with SmartSource paths such as `<gridName>.0.<columnName>.displayValue`. Preserve exact Baserow/source column names in those paths. They display rows; they do not compute: an `all_the_data` grid reads at most 1000 rows by default, any other grid gives a formula its selection only. Counts, sums and "already exists" checks come from source aggregations or a filtered source (Generation quality).
- Treat hidden source grids as reusable no-code data providers, especially for Baserow relationship data. They are useful when a visible component needs to render denormalized cards, dashboards, master-detail panels, or summaries based on `link_row` relations and `lookup`/reported fields without showing a table UI.
- For relationship-driven displays, create one hidden grid per needed table or relation view, include the link fields and lookup fields in `forms_config.columns`, and use Baserow filters/sorts to narrow the hidden grid to the relevant rows. Visible HTML can then compose readable rows from linked records and lookup values through SmartSource paths.
- Source-backed grids are populated when their page is displayed. Do not rely on a hidden grid located on a page that has not been shown yet to feed visible components on another page. Place hidden data-provider grids on the same page as the visible cards/summaries that consume them, or ensure the page containing the hidden grids is displayed before any dependent SmartSource rendering is needed.

### Baserow Source Pattern

- Write Baserow sources and saves with the reduced shapes of the contract's `baserowShorthand` section (in the core): `source: { table, columns, filter, sort, groupBy, aggregations }` on a grid, chart, map or gallery, `source: { table, field }` or `{ table, display, value }` on a choice list, `saveTo: { table, row, values }` and `deleteFrom: { table, row }` on a submit element. `table` is the table id (or its path) from `nocode-baserow-catalog-list`; the tools find the rest, encode the variables and resolve the references to fields (`{ field: "name" }`) and grids (`row`). Use the native shapes below only for what the shorthand does not express.
- A choice list whose answer fills a `link_row` column lists the rows of the linked table with `value: "id"` and a readable column as `display` (`source: { table: <linked table>, display: "Nom", value: "id" }`): the answer is the linked row id. A name as value is written as text and Baserow links the first row with that primary text, wrong for two rows of the same name. `nocode-form-create`, `nocode-form-edit` and `nocode-form-update` write `"id"` for a select they create or change (warning `link_row_select_value_rewritten`: conditions and formulas reading it get the id); `nocode-form-validate` refuses another value (`link_row_select_value`).
- The `columns` of a choice list's rows hold its displayed and stored values, `"id"` (the row id) included: C8Oforms refuses the rows of a select whose `displayValue` or `value` is not among them to the respondents of the published form, while your preview, as the owner of the source, still reads them. The reduced `source` and `nocode-form-create`, `nocode-form-edit` and `nocode-form-update` add them to a select they create or change (warning `select_columns_completed`), as No Code Studio does when it saves; `nocode-form-validate` refuses the gap (`baserow_select_columns`). A form already published keeps the refused source until it is published again.
- When the turn context names the tables of the current application or a selected database or table, they are the data target: use their ids directly, without searching the catalog. Use `nocode-baserow-catalog-list` first only when you need to discover which Baserow workspaces, bases, and tables are available to the authenticated No Code user; filter it by `databaseId`/`tableId`, or by `databaseName`/`tableName` when only a name is known, rather than reading the whole catalog page by page.
- Use `nocode-baserow-schema-apply` for schema work. It can plan or apply canonical schema JSON with `workspaceName`/`workspaceId`, `baseName`/`baseId`, `tables[].fields`, `tables[].views`, and `tables[].sampleRows`.
- Use `tables[].upsertKey` whenever applying sample rows to an existing table, so reruns update existing rows instead of creating duplicates.
- The answer of an apply lists, in `rows`, the rows it wrote as Baserow saved them (`id` and `values`, per table): that is the proof of the write. Do not read them again with `nocode-baserow-rows-list`. Adding rows to a table you just created (or that the turn context says is new) needs no read before either.
- `nocode-baserow-schema-apply` follows Baserow semantics: tables are Baserow tables; relationships are `link_row` fields; reported fields are `lookup` fields depending on an existing link field.
- The catalog tool returns `workspaces` > `bases` > `tables`, each listed once, and `counts`; base ids are Baserow database ids, and table ids are Baserow table ids. With `includeColumns`, each table lists its `columns`: `name`, `type`, `primary`, `readOnly`, the choices of a select (`options`) and the table a link points to (`linksTo`). `view:"full"` returns every raw Baserow property instead; you do not need it.
- The catalog tool is read-only discovery. It must not be used as permission to call low-code requestables or raw Baserow APIs.
- A component is connected to Baserow when it has an enabled `sources["lib_BaseRow.formssource_GetTableData"]` entry (a map: `sourcesMarkers`, see Maps).
- The live Baserow binding is stored in `sources["lib_BaseRow.formssource_GetTableData"].vars.forms_config.str`, a JSON string. Parse that string instead of reading it as plain text.
- A filter value that reads a field is `{ field: "name" }` in the reduced `source`: the tools write the reference with the id the field is saved with, a field added in the same edit included. In a native filter written by hand, a reference `$$START<id>{...}END<id>$$` carries the id of the component it reads; for a component added in the same `nocode-form-edit`, its name in place of the id (or a `c8opath` starting with its name) is replaced by its saved id (`referencesResolved` in the answer). A reference whose id names no component is refused for what the write brings, reported for what the form already had (`unknown_reference_id`).
- When you write a source or a backend action, you may give `forms_config` as a JSON object, `forms_freeVars` as `{ "Column": value }` and the other variables as plain values (`"forms_id": ""`, `"forms_tableGroupBy": "Status"`): the tools encode them as the editor does (`{ str, html:false }`, and the `[{ name, str }]` list for `forms_freeVars`). Filters and sorts keep their `conds` shape.
- Treat `forms_config.str` as the source of truth for the Baserow table and dynamic output columns. Inspect `table_id`, `table_id_int`, `columns`, `hidden`, `link_row_table_id`, `source_id`, and `source_owner`.
- `table_id` is the human-readable Baserow path, commonly shaped like `Workspace~>Database~>Table`; `table_id_int` is the numeric Baserow table id.
- The effective Baserow output columns are dynamically deduced from `forms_config.columns`, with `forms_config.hidden` indicating hidden columns.
- The source variables sit next to `forms_config` under `sources["lib_BaseRow.formssource_GetTableData"].vars`. `forms_tableFilter`, `forms_tableSort`, `forms_tableDistinct`, `forms_tableGroupBy`, and `forms_tableAggregations` carry optional query behavior. Empty strings mean no extra filter, sort, distinct, grouping, or aggregation is applied; populated `conds` arrays describe active filter/sort criteria. `forms_tableAggregations` takes the aggregations of the footer of a Baserow grid (`authoringContract.baserowSources.groupAggregations.operators`), one value per group with `forms_tableGroupBy`, or one row for the whole table without it.
- Use `nocode-form-get` for inspection. If the read tool is unavailable, report the missing capability.

### Maps

- A map shows the rows of a table as markers. Bind it with `source: { table, title, latitude, longitude, filter, sort }`, each of `title`, `latitude` and `longitude` naming a column of the table, whatever its name (`columns: [title, latitude, longitude]` in this order works too). The same goes for `update_field` with `patch.source` on an existing map.
- `title` is the text of a marker, and also its tooltip and its popup: the viewer shows one column for the three, so `popup` is accepted only as another name for `title`. `latitude` and `longitude` are number columns in decimal degrees (45.764, 4.8357); a date, select or link column there puts no marker (warning `map_marker_column_type`).
- The tools write it as No Code Studio does, where the viewer reads it: `sourcesMarkers["lib_BaseRow.formssource_GetTableData"]`, the first entry of `sourcesMarkers`, with `forms_config.columns` `[title, latitude, longitude]`, and `config.sourceMarkersEnabled: true`. The viewer never reads `sources` on a map: table data written there is moved to `sourcesMarkers` by the tools, and `nocode-form-validate` reports a map that still has it (`map_source_not_read`).
- A filter or a sort narrows the markers like the rows of a grid (`forms_tableFilter`, `forms_tableSort` next to `forms_config`). Reading a saved map, look at `sourcesMarkers` and `config.sourceMarkersEnabled`, not `sources`.
