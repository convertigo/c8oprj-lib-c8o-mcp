# Convertigo Authentication

## When to read this
Read this when a feature adds or changes login, logout, sign-up, password reset, OAuth 2.0, OpenID Connect, FranceConnect, or access control on sequences. Also read it before replacing the `auth_login` skeleton generated by `upsert-crud`: that skeleton accepts any password.

## What this guide covers
- The engine session model and what actually protects a requestable.
- Choosing a flow and the marketplace library that implements it.
- The application-side golden path shared by every flow: configuration sequence, login facades, protected business sequences, logout.
- OAuth / OIDC with `lib_OAuth`, FranceConnect with `lib_FranceConnect`, email + password with `lib_UserManager`.
- The NGX client side, secrets, validation proof, and completion checks.

## Session and exposure model

The authenticated user is an attribute of the HTTP session. `SetAuthenticatedUserStep` (or `context.setAuthenticatedUser(id)`) writes it, `RemoveAuthenticatedUserStep` (or `context.removeAuthenticatedUser()`) clears it, and every project called by the same client session sees the same user. A login performed by a library sequence therefore authenticates the application sequences called afterwards.

What protects a requestable:
- `authenticatedContextRequired=true` is the only runtime check that requires a logged-in user. Without it, a requestable is anonymous.
- `Hidden` does not protect anything. It only hides the requestable from the Test Platform and WSDL; any client can still call it.
- `Private` blocks direct HTTP calls only. Internal calls (`SequenceStep`, `TransactionStep`) bypass accessibility, so anything an anonymous sequence calls is anonymously reachable too.
- A sequence without an `accessibility` line is `Public`; a transaction without one is `Private`.
- URL mappings (`UrlMapper`) ignore `accessibility`: a `Private` target behind a mapping is reachable from outside and only its `authenticatedContextRequired` protects it. The only built-in mapper authentication is Basic (`authRequestable` receives `user` and `password`); validate a Bearer token inside the target sequence.

Consequences that are easy to miss:
- In Studio mode `Private` requestables are callable from outside. A call that succeeds in the Studio proves nothing about exposure; use `project-security-audit` for exposure and `requestable-execute` only for behavior.
- A client can request a stub with `__stub=true`, and stubs bypass the authentication check. Never put real data in a stub of a protected requestable.
- The session id is not renewed at login. Always end the session at logout (see the golden path) so a session cannot be reused by another user.
- With `corsOrigin` `=Origin` (the engine default through `=Global`) and the engine property `convertigo.xsrf.projects` off (its default), any website can call sequences in the browser of a logged-in user. Restrict `corsOrigin` to the known origins of the application.
- `HttpConnector.trustAllServerCertificates` defaults to `true`. Every connector that talks to an identity provider or a mail relay must set it to `false`.

## Choosing a flow

| Need | Implementation |
|---|---|
| Google, GitHub, LinkedIn, Azure AD, generic OpenID provider | `lib_OAuth` |
| FranceConnect | `lib_FranceConnect`, the reference OpenID Connect implementation |
| Email + password accounts (sign-up, confirmation, sign-in, reset) | `lib_UserManager` (accounts stored in FullSync) |
| Corporate directory | `lib_UserManager.SignInLDAPBulk` / `SignInADBulk`, or `LDAPAuthenticationStep` |

Import the library with `marketplace-import` and keep the reference pinned on a released tag or version branch. Do not reference a moving branch with `autoPull=true` for a security library.

Each flow authenticates the session with a provider-prefixed user id: `google:<sub>:<email>`, `azuread:<id>:<upn>`, `openid:<sub>:<name>` for `lib_OAuth`, `fc:<sub>` for FranceConnect, the email for `lib_UserManager`. Base authorization decisions on that id, never on a value sent by the client.

## Golden path (every flow)

1. **Import the library, pinned.** `marketplace-list` to find it, then `marketplace-import`. Check the symbols it expects with `project-list-symbols`.
2. **Configure with symbols, server side.** Client ids, endpoints, redirect URIs, scopes, and SMTP settings are symbols. Secrets use a name ending with `.secret` and no default value that holds the real secret.
3. **Expose public configuration through a configuration sequence.** Symbols are resolved on the server only; NGX pages and TypeScript never see them. The client gets `client_id`, the authorization endpoint, the redirect URI, the scopes, and a per-login `state`/`nonce` from a configuration sequence, as the libraries already do (`lib_FranceConnect.getConfiguration`, `lib_OAuth.GetOAuthCredentials`). Rules for that sequence:
   - `Hidden`, anonymous by design (the client calls it before login). Record its `EXP-02` audit finding with `suppress` and the reason.
   - It returns public values only. Never a `.secret` symbol, never a token.
   - It generates `state` and `nonce` with `SecureRandom` and keeps them in the session; the login sequence checks them once and removes them.
   - Never hard-code a client id or an identity-provider URL in NGX code.
4. **Log in through application facades.** Create `Hidden` sequences in the application project (for example `auth_loginGoogle`, `auth_signIn`) that call the library with `SequenceStep` and `StepVariable` children:
   - only the values that genuinely come from the user reach the library from the client: the authorization `code` and `state`, or the email and password;
   - every other library input is set on the `StepVariable` from a symbol: `client_id`, `redirect_uri`, `keySecret`, endpoints, email subject, logo, and application name;
   - the facade does not declare those as its own `RequestableVariable`, so the client cannot override them.
5. **Protect business sequences.** Every business sequence is `Hidden` with `authenticatedContextRequired=true`. Helpers and every transaction stay `Private`.
6. **Log out by ending the session.** A logout sequence runs `RemoveAuthenticatedUserStep` then `RemoveSessionStep`. The client calls it with `__disableAutologin=true`; otherwise the SDK replays the last successful login request as soon as the session is lost.

## OAuth / OpenID Connect with lib_OAuth

Entry points (the sequence the client-facing facade calls):

| Provider | Library sequence | User input | Server-side `StepVariable` values |
|---|---|---|---|
| Google | `lib_OAuth.loginGoogleWithCode` | `code` | `client_id` = `${lib_oauth.google.clientid=...}`, `keySecret` = `${lib_oauth.google.keysecret.secret=...}`, `redirect_uri` = the application redirect symbol |
| GitHub | `lib_OAuth.loginGitHubWithCode` | `code` | `lib_oauth.github.clientid`, `lib_oauth.github.keysecret.secret`, redirect symbol |
| LinkedIn | `lib_OAuth.loginLinkedInWithCode` | `code` | `lib_oauth.linkedin.clientid`, `lib_oauth.linkedin.keysecret.secret`, redirect symbol |
| Azure AD | `lib_OAuth.loginAzureAdWithAccessToken` | `access_token` | `lib_oauth.azuread.clientid`, `lib_oauth.azuread.tenantid` |
| Generic OpenID | `lib_OAuth.loginOpenIDWithAccessToken` | `access_token` | `introspectURL` = `${lib_oauth.openid.instrospect_url=...}` (spelling as declared by the library), `lib_oauth.openid.clientid`, `lib_oauth.openid.clientsecret.secret` |

Rules:
- Never let the client choose `introspectURL`, `client_id`, `redirect_uri`, or `keySecret`. An attacker-controlled introspection or token endpoint can declare any user valid.
- The public client configuration comes from `lib_OAuth.GetOAuthCredentials` (client ids, Azure tenant, OpenID endpoint) or from an application configuration sequence that also issues `state`.
- `lib_OAuth.SignOut` removes the user and the stored provider token; call it with `__disableAutologin=true` and end the session.
- NGX `OAuthLoginAction` (providers `azure`, `linkedin`, `openid`): set `clientid` from the configuration response, `callbackurl` to the registered redirect page, and `loginRequestable` explicitly to the application facade. For `openid` the built-in default `lib_OAuth.loginOpenID` does not exist, so the action fails without an explicit `loginRequestable`.
- Provider tokens stay in the session (`oAuthAccessToken`). Do not return them to the client.

## FranceConnect with lib_FranceConnect

`lib_FranceConnect` is the reference pattern for OpenID Connect and shows every check a correct implementation performs:
- `getConfiguration` (Hidden) returns `OpenIDClientID`, `AuthorizeEndPoint`, `RedirectURI`, `Scopes`, `State`, and `Nonce`; `State` and `Nonce` are random and kept in the session.
- `loginWithCode(code, state)` (Hidden) checks and consumes `state`, exchanges the code server side with the client secret, verifies the id_token signature against the provider keys, checks `iss`, `aud`, `exp`, and `nonce`, then authenticates `fc:<sub>`.
- `checkAccessOpenID` (Hidden) restores an existing session; `Logout` (Hidden, authenticated) ends the FranceConnect session.
- The NGX shared component `FranceConnect` drives the flow: it calls `getConfiguration`, redirects to the authorization endpoint, then calls `loginWithCode` with the `code` and `state` read from the callback URL and removes them from the address bar.

Configuration symbols: `lib_franceconnect.clientid`, `lib_franceconnect.scopes`, `lib_franceconnect.authorize`, `lib_franceconnect.tokenendpoint`, `lib_franceconnect.issuer`, `lib_franceconnect.redirecturi`, `lib_franceconnect.endsession`, `lib_franceconnect.postlogouturi`, `lib_FranceConnect.client_secret.secret`, and `lib_FranceConnect.corsOrigin`. The library defaults target the FranceConnect sandbox; production must define every one of them on the engine.

## Email + password with lib_UserManager

Email + password accounts always use `lib_UserManager`. Never store, hash, or verify passwords in application code or in an application database, even for a demo or when the project data lives in SQL: accounts live in the library, business data stays where it is.

Prerequisites and what to do when one is missing:
- **FullSync available on the engine.** Accounts are FullSync documents keyed by email. If FullSync is not available, stop and tell the user; do not switch to another storage.
- **SMTP relay** (`lib_UserManager.smtp.*` symbols). Sign-up confirmation and password reset send emails; sign-in does not. Without a relay, still implement the email flows with the library, keep the symbols as placeholders, validate sign-in with a demo account, and report the email flows as implemented but functionally unvalidated.
- **Accounts created by an administrator.** `lib_UserManager.AddUser` with `askForPasswordReset=false` creates an already confirmed account without email. It is `Private` and requires an authenticated session, even when called from another sequence, so it belongs to an administration flow of a signed-in user; it cannot create the very first account.

### Demo or first account without SMTP
Use this recipe on a development engine to get a working account without a mail relay. It runs from the Studio with `requestable-execute` and adds nothing to the project:
1. Call the application sign-up facade, or `lib_UserManager.CreateAccount`, with the demo email and password. The library hashes the password and writes the account document, then stores a confirmation key in it before it tries to send the email. Without a relay the call ends with an SMTP error, but the account and its key exist.
2. Read the account: `lib_UserManager.lib_usermanager_fullsync.GetAccountDocument` with `{"_use_docid":"<email>"}`, and take `account.passwordResetKey`.
3. Confirm it: `lib_UserManager.ConfirmAccount` with `email` and that `passwordResetKey`. The account becomes `confirmed` and `SignIn` works.

Do not write an account document by hand or compute its password hash: the document and hash formats belong to the library and change with its versions. Do not add an anonymous sequence that creates or confirms accounts to make a demo work. Report the demo account to the user as a development-only step.

Any deviation from the library is announced to the user and agreed before the project is changed, not justified afterwards.

Flows, in order:

| Step | Library sequence | User input | Server-side values |
|---|---|---|---|
| Sign-up | `lib_UserManager.CreateAccount` | `user` (email), `password`, `lang` | `emailSubject`, `emailLogo`, `targetApplicationName` from application symbols |
| Confirmation | `lib_UserManager.ConfirmAccount` (called by `CreateAccount` to send the link) | `email`, `passwordResetKey` from the confirmation link | same email settings |
| Sign-in | `lib_UserManager.SignIn` | `user`, `password`, optional `rememberMe` | — |
| Reset request | `lib_UserManager.ForgotPassword` (or `ForgotPasswordWithBrand`) | `email` | `emailSubject`, `emailBody`, `emailLogo`, `targetApplicationName` from application symbols |
| Reset | `lib_UserManager.ForgotPassword` | `passwordResetKey`, `newPassword` | — |
| Password change | `lib_UserManager.ModifyPassword` (authenticated) | `password` | `user` from `context.getAuthenticatedUser()`, never from input |
| Sign-out | `lib_UserManager.SignOut` | optional remember-me `token` | removes the remember-me token and the authenticated user; the facade still ends the session |

Rules:
- Wrap each step in an application facade. The facade never forwards `emailSubject`, `emailBody`, `emailLogo`, or `targetApplicationName` from the client: those let anyone send arbitrary content through your mail server.
- The sign-in facade returns one generic error for every failure (unknown user, wrong password, unconfirmed account) so the response does not reveal which accounts exist.
- Add a proof-of-work captcha on sign-up and reset requests: `lib_Captcha.altcha_createChallenge(action)` on the client side, then `lib_Captcha.altcha_verifyPayload(payload, expectedAction, preventReplay=true)` in the facade before calling `lib_UserManager`.
- Configure the mail relay with the `lib_UserManager.smtp.*` symbols (`server`, `port`, `user`, `sender`, `authtype`).
- Build links sent by email from a base-URL symbol, not from the request host: the host header is client-controlled.
- Schedule `lib_UserManager.RemoveDraftedAccounts` to purge unconfirmed accounts.
- Password hashing and comparison belong to the library. Application code never computes a password hash.

## NGX client

- Symbols are not available in NGX. Every public setting arrives from the configuration sequence; keep the response in page or shared state, never in source code.
- The login page is a form built as described in the NGX forms guidance: `UIForm` (for example `loginForm`) > `FormItem` > `Input` for the email (`Type` `email`, `Required`) and for the password (`Type` `password`, `Required`), each with its `Label` property and `LabelPlacement` `stacked`, then a `SubmitButton` and the form `onSubmit` event.
- The `onSubmit` event calls the application facade with `CallSequenceAction`, whose `UIControlVariable` values come from the Form SmartSource. Set `noAutoLogin` ("Disable auto login") to `true` on the sign-in, sign-up, and sign-out calls; otherwise the SDK replays the stored login request and can loop.
- Sign-in failures come back as a normal response with an `error` element, so the action's Failure handler does not fire. Put an `IfAction` on `out?.error` as a child of the call to show the generic message, and the navigation in the success child. The result toast is a child of the call, never a sibling: siblings under an event run in parallel (see the NGX authoring invariants).
- The client knows it is authenticated from the facade response or the `X-Convertigo-Authenticated` response header; re-check with the library check sequence (`checkAccessOpenID`, `checkAccessToken*`) on application start.
- Logout calls the logout facade with `noAutoLogin` set to `true` (it sends `__disableAutologin=true`), then clears client state in a child action.
- After an OAuth or OIDC redirect, read `code` and `state` once from the URL, then remove them with `history.replaceState`.
- Never store passwords, provider tokens, or `code` in `localStorage` or `sessionStorage`.

## Secrets
- Secrets live in symbols whose name ends with `.secret`, defined on each engine. The default value in the project is a harmless placeholder.
- Variables that carry a password, token, secret, or authorization header set `visibility` to `15` (Logs=1, Studio=2, Platform=4, XmlFile=8). An even value leaves the value in the logs.
- Connectors to identity providers and mail relays set `trustAllServerCertificates=false`.

## Minimum validation proof
For a credible authentication feature, you need, with `requestable-execute`:
- an anonymous call to one business sequence fails with an authentication error;
- the login facade succeeds with a real test account or provider, then the same business sequence succeeds;
- after the logout facade, the business sequence fails again;
- a wrong password (or an invalid `state`) fails with the generic message.

Then run `project-security-audit({project})`: `AUTH-*`, `EXP-*`, and `SEC-*` rules are `passed`, `notApplicable`, or `suppressed` with a written reason (for example the anonymous configuration sequence). A login that "works" in the Studio is not an exposure proof.

## Anti-patterns / do not do
- Do not ship the `auth_login` skeleton generated by `upsert-crud`; replace its body with a facade that calls the library (`lib_UserManager.SignIn` for email + password).
- Do not store, hash, or verify passwords in application code or tables, and do not replace a library flow because SMTP or a test provider is missing: implement with the library and report what could not be validated.
- Do not rely on `Hidden` or `Private` to protect a business sequence.
- Do not accept a client id, redirect URI, endpoint, introspection URL, secret, or email content from the client.
- Do not return a secret, a provider token, or a password hash to the client.
- Do not hard-code identity-provider settings in NGX code; use a configuration sequence.
- Do not log out with `RemoveAuthenticatedUserStep` alone, or without `__disableAutologin=true`.
- Do not reveal whether an account exists in sign-in, sign-up, or reset responses.
- Do not reference a security library on a moving branch with `autoPull=true`.

## Completion checks
- The library is imported and pinned on a released tag or version branch.
- Every required symbol is defined; secrets use `.secret` symbols without real defaults.
- The configuration sequence returns public values only and issues `state`/`nonce` for redirect flows.
- Login facades pass only user-provided values from the client; everything else comes from symbols.
- No password is stored, hashed, or verified in application code; email + password accounts live in `lib_UserManager`.
- Every business sequence is `Hidden` with `authenticatedContextRequired=true`; helpers and transactions are `Private`.
- Logout ends the session and the client calls it with `__disableAutologin=true`.
- The validation proof above is green and `project-security-audit` has no unexplained authentication, exposure, or secret finding.
