# Act on verifier reports and close the task

Read when: Act on verifier reports and close the task. Summary: `convertigo://guides/common`.
Previous: `convertigo://guides/common/proof`. Next: `convertigo://guides/common/seed`.

---

- Acting on the report (`report` of `subagent-run`, the top level of `browser-verify`): `verdict:"passed"` closes the proof; quote its evidence and screenshot paths. A `failed` check or a visual defect is a finding about the app: fix it in the source objects, rebuild, then call `browser-verify` again for the affected paths only. The sub-agent can be wrong: when a check is `not_checked`, or its evidence contradicts what you know of the data, read the named screenshot with `image-describe` or make one targeted Playwright check yourself before changing code. Never rerun the same verification unchanged to get another verdict. The sub-agent only observes and never edits the project: the decision and the fixes stay yours.
- Without a verifier (the tool is missing, or it reports no viewer or a gateway error), prove each path with the dedicated Playwright tools: `browser_navigate`, `browser_snapshot`, `browser_fill_form` (all the fields of a form in one call), `browser_click`, `browser_evaluate` (the values of a page read in one call) and `browser_take_screenshot` with `filename: ".playwright-mcp/<page>.png"` on each page; fix and retry the path when a check fails. `browser_wait_for` counts `time` in seconds, 30 at most: `{time: 2}` waits 2 s, `{time: 2000}` waits the whole 30 s. To wait for a page, give a text it shows, `{text: "<its title>"}`: the call returns as soon as the text appears. In the Studio viewer, three things make a click wait 30 s and fail: the Studio's build progress widget (a `div` holding a 100x100 `canvas`, centred on the page) takes the clicks above Ionic overlays, so start each path with one `browser_evaluate` of `() => document.querySelectorAll('body > div').forEach(d => { if (d.firstElementChild && d.firstElementChild.tagName === 'CANVAS') d.style.pointerEvents = 'none'; })`; an `ion-select-option` is never visible, so click the `ion-select`, then the option text in the alert or popover it opens, then the alert's OK; and an `ion-input` is filled through its inner `input` (`ion-input input`).
- Pages behind the sign-in, in a Studio: call `viewer-sign-in({project, user, page})` with an account of the app (the demo account the notes or the brief name, or the one the user gives): the Studio browser, the one of your Playwright tools and of the verifier, is then signed in as that account without its password, on that page. Then check the page; never fill the sign-in form for a check. On a server, or when the page still asks to sign in (the app keeps state of its own at sign-in), ask the user for the account to use.
- Never guess, try, crack or brute-force a password, never read, compute or compare stored password hashes or salts, never reset or change an account's password, and never create an account or write one in the database to get past a sign-in. A password you do not have is asked to the user or replaced by `viewer-sign-in`; nothing else.
- To look at one screenshot when your model cannot read images (it has no image input, or a screenshot is refused): save it with `browser_take_screenshot` and a `filename` (with a filename the image is only saved, not sent to your model), then call `image-describe({path:"<the file>", question:"<what to check>"})` with one precise question. Keep the default `reasoning` (none) and `maxTokens`; one call per page state is enough.
- A single hydrated DOM sample proves only that the viewer rendered that state. For timers, live updates, interactions, or other changing behavior, require two observations showing the expected change or an equivalent browser-control assertion.
- If browser control is unavailable (`browserControlError`), report the result as implemented but functionally unvalidated, every page NOT verified. Do not claim success merely because compilation and server logs are green.
- Prove a delete, or a right that allows one, on a row you create for the proof, never on a row the user already had: create it, run the delete with the allowed account and check it is gone; with a refused account check the refusal and that the row is still there, then delete it with the allowed one. A delete proven on an existing row loses the user's data.
- Stop after the requested behavior is green. Do not add an unsolicited polish pass, do not restart broad verification, and do not repeat proof that cannot change the conclusion.
- Before the final summary, call `project-changes` (with `project` when the task is about one project) and write the summary from it. Name every object, file and run it lists. Say which listed objects the user did not ask to change. Name every object of `unproven` as not verified, or prove it first. Never write "nothing else was modified" unless the list shows it, and never call a run proof when its last status is an error. The list holds only what went through the MCP. Delete the objects it lists under `temporary` (probes, tests you created) before reporting, unless the user asked for them; an SQL expression is tried with `sql-select`, never with a transaction created for the trial.
- When the MCP lists `report-create`, the user agreed to send feedback to Convertigo: file at most one short report per turn for a reusable friction of a Convertigo tool, guide or prompt that you had to work around (what you expected, what happened, how you got past it). Never report your own mistakes or a refusal you fixed at once, and never put project data, names or credentials in it.
