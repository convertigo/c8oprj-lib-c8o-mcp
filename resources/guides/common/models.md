# Models, templates and output contracts

Read when: Models, templates and output contracts. Summary: `convertigo://guides/common`.
Previous: `convertigo://guides/common/existing-project`. Next: `convertigo://guides/common/batching`.

---

## Start from what exists, and keep its contracts

- To start a page, a sequence or any object from a model or from an existing one (a page the user names as a model, a sequence that already does most of the job), copy it with `databaseobject-copy({source, target, name})`, then adapt the copy with `databaseobject-tree-apply` on the QNames of its new place: its texts, bindings, the sequence it calls, its route segment. Never rebuild it from `databaseobject-tree-get` reads: a copy keeps every property and gives the copy its own step and component priorities, so its sources point at its own objects. Read only the parts you change: the answer of the copy lists its objects one line each (`structure`), with the QNames to patch; copy as soon as the model is chosen, then work from those lines.
- When a skill or the project names a model page or a template (one per kind of page: standard, sign-in, sign-out, error pages), every page of that kind starts as its copy: `databaseobject-copy` from the project that holds it, a referenced project or library included. Never `ngx-page-create` for such a page: it generates its own structure. Never rebuild the model from reads, and never create a local equivalent. A model that cannot be found stops the work: say so, and generate nothing in its place.
- Fill only the model's content zone, the area it leaves for the page's own content. Never delete, move or restyle its other zones (header, toolbar, menu, footer), and never change the model itself: the copy leaves it untouched. Set the copy's route segment and title, which it gets anew.
- Add the content inside the zone: `databaseobject-tree-apply` with the zone as target and `at:"inside"`, or `at:"self"` with `mode:"merge"` and the new children. Never `mode:"replace"` on the zone: it keeps its own attributes and styles (its class gives it its look), and a placeholder the model left in it goes with `databaseobject-delete`.
- Before reporting, compare the page with its model (`databaseobject-tree-get` of both, two or three levels): the same zones, in the same order, only the content zone filled. Say in the report that it matches, or what differs and why.
- A copy into another project keeps its references to the source project (calls, sequences, styles) unless you pass `retargetProject:true`; the answer lists what the copy still reads outside itself. Fix those before anything else.
- The output of an existing sequence or transaction is a contract other pages and sequences consume. A new page binds to that output as it is (its keys and their case): adapt the page's bindings, never the requestable. Do not change an existing requestable's output, its keys, its steps or its SQL aliases unless the user asked for it; when the page needs a field the output lacks, add a new requestable or ask. `databaseobject-tree-apply` refuses a change inside a requestable that existed before the conversation, and changes nothing, until `changeExisting` names it: when the user asked to change it, send `changeExisting:["<its QName>"]` with the first change; otherwise create a separate object or adapt the caller. A change the user did not ask for is named as such in the final report, and the report names every requestable `project-changes` lists under `existingChanged`.
- A text the user gave (a title, a label, a button text) is written as given. A `project-lint` text finding (language, spelling) never changes it: when it disagrees with the app's language, tell the user instead.
